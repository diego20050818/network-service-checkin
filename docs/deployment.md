# 部署 升级与回滚

## 构建

```powershell
npm.cmd ci
npm.cmd run verify
npm.cmd run package:win
```

`electron-builder` 生成 x64 NSIS 安装包、`.blockmap` 和 `latest.yml`。模板通过 `extraResources` 随安装包发布；数据库和导入源文件副本写入 Electron `userData/data`，不写安装目录。

当前开发构建未配置代码签名证书，安装包的 Authenticode 状态为 `NotSigned`。正式分发前应使用组织证书签名，并在目标机验证签名链和 SmartScreen 表现。

## 首次部署

1. 在无 Node、Python、Office 的 Windows 10/11 x64 验收机安装。
2. 断网启动，导入客户最新排班和成员信息。
3. 按需求 01-28 执行真实验收并记录耗时、系统版本和缩放比例。
4. 完成一次手动备份、一次恢复和一次安装包卸载重装验证。

## 升级

### 0.6.3 稳定版

发布构建位于 `apps/desktop/release/candidate-0.6.3/`，正式文件由 GitHub Release v0.6.3 提供。应用标识、userData 目录、数据库 schema v4 和 GitHub 稳定更新通道保持不变；v0.6.0 可直接向前更新。班次时段配置和提醒去重状态写入既有 `settings` 表，不要求数据库迁移。具体验证范围见 [v0.6.3 发布验证报告](v0.6.3-release-validation.md)。

### 0.6.0 历史稳定版

发布构建在本地位于 `apps/desktop/release/candidate-0.6.0/`，正式文件由 GitHub Release v0.6.0 提供。应用标识和 userData 目录不变。0.5.x 可由原更新器升级；0.4.0 可直接手动覆盖安装 0.6.0。

首次启动发现旧 schema v2/v3 时，先在 `userData/data/upgrade-backups/` 生成包含数据库、排班源、成员源和模板的升级备份，验证完整性和文件哈希后才迁移到 v4。失败停止启动，升级备份不参与每日备份轮换。

旧库只能向前升级。回退时先保存当前 v4 数据目录副本，再取升级前备份中的 `app.sqlite3` 及对应来源文件，在应用完全退出后恢复到原数据位置，最后安装旧版。不要先打开旧版读取 v4 数据库；回退后的数据时点为该升级前备份，升级之后新增的记录不在其中。

备份恢复会先在临时副本迁移、检查完整性和外键，再生成当前库的 `pre_restore` 备份并替换；同名不同内容的归档源文件会阻止恢复。具体证据及尚未完成的安装环境验收见 [升级验证报告](v0.6.0-upgrade-validation.md)。

### 0.5.x 历史说明

升级前在“设置 > 备份管理”执行“立即备份”。数据库迁移只允许向前追加且在事务中执行；0.4.0 的 schema v2 数据库和 manifest v2 备份可由 0.5.x 自动迁移，备份清单格式不变。0.5.x 备份不承诺可交给旧版恢复；0.5.1 相对 0.5.0 无 schema 变更，无需迁移。

0.4.0 没有更新器且对应 Release 没有 `latest.yml`，必须先手动安装任一 0.5.x（如 0.5.1）。此后可在设置中选择：

- 手动：检查更新、下载、确认重启安装；默认值，不主动联网。
- 自动：窗口启动完成后检查一次，发现稳定版后后台下载，完成后仍须确认重启。

发布 Release 时必须同时上传 `network-service-checkin-<版本>-x64.exe`、同名 `.blockmap` 和 `latest.yml`。发布前校验 `latest.yml` 的版本、安装包文件名和 SHA-512。

## 回滚

若新版本启动或迁移失败：

1. 保留失败版本的数据目录副本和日志。
2. 卸载应用但不删除用户数据。
3. 安装上一已验收版本。
4. 如数据库已发生不兼容迁移，从升级前备份恢复并重启应用。

恢复会替换当前数据库，因此无论从备份列表还是其他位置恢复，界面都会先明确提示；恢复前还会自动生成 `pre_restore` 安全备份。
