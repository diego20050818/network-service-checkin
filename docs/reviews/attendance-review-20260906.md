# 签到打卡功能审查

审查日期：2026-09-06

## 结论

实时签到主路径具备班内时间校验、成员和席位校验、整批事务、重复请求幂等、数据库唯一约束以及撤销恢复能力。当天班次现在会自动刷新，避免跨过开班时间后页面仍停留在旧状态。

人工补记仍有一项需要单独确认业务口径的高风险问题，因此本次没有擅自修改。

## 已确认问题

### 高：人工补记允许未来班次和班外历史时刻

`attendance-service.ts` 的人工补记只检查班次是否有效、席位是否占用和成员是否有效。填写历史时刻时，仅解析时间并据此判断迟到，没有验证日期等于班次日期，也没有验证时刻位于 `[开始, 结束)`；不填历史时刻时，也允许给未来班次提前生成完整计薪记录。

影响：错误日期、班外时间或未来班次都可能直接产生完整班次工时，并进入看板和工资输出。

建议：确认补记政策后，默认只允许已开始或已结束班次；填写历史时刻时要求日期匹配且处于班内。确需例外时，应增加“强制补记原因”而不是静默接受。

### 中：错误的历史打卡时刻不能直接更正

数据库审计类型预留了 `set_punch_time`，但当前服务和界面只支持更正人员、撤销和恢复。历史时刻填错后只能撤销记录再补记，操作步骤多，也容易留下两条容易混淆的记录。

建议：在确定上述补记校验规则后，再增加带变更日志的“更正打卡时刻”。

### 低：系统信任本机时钟

普通签到由主进程读取 Windows 本机时间。它符合当前离线需求，但手动修改系统时间会影响签到和迟到判定；当前没有可信时间源、账号或操作者身份。

建议：继续将其作为单机离线系统的已知边界；若未来用于强审计场景，再引入受控时间源和身份机制。

## 已验证保护

- 普通签到只允许 `[开始, 结束)`，结束时刻不可签到。
- 同一席位最多一条有效记录，同一成员不能占同班两个席位。
- 多人签到整批写入，任何一项失败不会留下部分记录。
- 同一席位和成员重复提交返回原记录，不重复计薪。
- 临时替班只改变实际人员，原负责人仍保留。
- 更正、撤销和恢复均保留变更记录，恢复前检查席位和成员冲突。
- 当前页面显示当天全部班次，并每 30 秒刷新可签到状态。
